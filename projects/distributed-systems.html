A reliable transport protocol on UDP

UDP drops, duplicates, and reorders packets. Our protocol gives applications reliable, in-order messages on top of it, with one client implementation and one server that handles many clients. Both sides run as an event loop: a reader goroutine hands packets over channels to a single routine that owns all connection state, so none of it needs locks.

  • Sliding window: a message goes out only while it fits in the window and the count of unacknowledged messages stays under a cap; the rest wait in a queue that drains as acknowledgements arrive, including cumulative ones.
  • Retransmission is driven by epochs, with exponential backoff tracked per message.
  • Failure detection: a peer that stays silent for a set number of epochs is declared lost; connection setup retries the same way.
  • Integrity and order: the receiver checks size and checksum, drops corrupted messages, and buffers early arrivals until the gap is filled.

Raft consensus

Raft keeps a replicated log consistent while servers crash and restart. I implemented leader election and log replication.

  • Election: each server is a follower, candidate, or leader, driven by one state-machine goroutine. A follower that hears no heartbeat within a randomized 400–600 ms timeout starts an election; a candidate with votes from a majority becomes leader, and voters refuse candidates whose logs are behind theirs.
  • Replication: the leader sends heartbeats every 105 ms, tracks how far each follower's log matches its own, backs up on a mismatch, and commits an entry once a majority holds it.

A replicated key-value store on actors

A key-value store spread over several servers, each running a group of actors that own copies of the data and talk only by messages. Clients can read and write at any actor; replicas converge without coordination.

  • Actor runtime pieces: an unbounded mailbox whose sends never block, and remote messages delivered as asynchronous RPCs.
  • Consistency: last writer wins, by timestamp with the actor ID as a tie-breaker.
  • Sync: each actor batches recent writes and sends them every 100 ms to its local peers, but to only one actor on each remote server, which keeps cross-server traffic down.
  • Joining: a new server announces itself, and existing servers push it their full state.
